# Repository Guidelines

## Project Structure & Module Organization
This project is a TypeScript CLI + web UI split into two main modules:
- `api/`: Hono-based server, CLI entrypoint, file watching, and Claude history storage logic (`index.ts`, `server.ts`, `storage.ts`, `watcher.ts`).
- `web/`: React + Vite frontend (`app.tsx`, `components/`, `hooks/`, `utils.ts`, `index.css`).

Build output goes to `dist/` (generated by `tsup` and Vite). Root config files include `tsconfig.json`, `package.json`, and `pnpm-lock.yaml`.

## Build, Test, and Development Commands
Use `pnpm` (lockfile is `pnpm-lock.yaml`) and Node.js 20+.
- `pnpm install`: Install dependencies.
- `pnpm dev`: Run frontend and backend in watch mode concurrently.
- `pnpm dev:web`: Start Vite dev server for `web/`.
- `pnpm dev:server`: Run backend with `tsx watch`.
- `pnpm build`: Build server and web assets for production.
- `pnpm start`: Run the built CLI/server from `dist/index.js`.

## Coding Style & Naming Conventions
- Language: TypeScript (`strict` mode enabled in both root and `web` tsconfig).
- Indentation: 2 spaces; keep trailing commas where formatter adds them.
- Strings: double quotes are the existing convention.
- Naming:
  - Files: kebab-case for React/component files (for example `session-view.tsx`), lowercase for entrypoints.
  - Types/interfaces: PascalCase.
  - Variables/functions: camelCase.
- Formatting: use Prettier (`pnpm exec prettier --write .`) before opening a PR.

## Testing Guidelines
There is currently no automated test suite in this repository. For changes, validate with:
- `pnpm build` (must pass).
- `pnpm dev` manual checks for core flows: session list loading, search/filtering, SSE live updates, conversation rendering, and resume-command copy behavior.

When adding tests, colocate them near source files or under a top-level `tests/` directory and use `*.test.ts` / `*.test.tsx` naming.

## Commit & Pull Request Guidelines
Recent history favors short, imperative commit messages (for example `Add resume command`, `fix: scroll jumping issue`).
- Keep commits focused and logically scoped.
- Use imperative subject lines; optional `fix:` prefix is acceptable.
- Reference issues/PRs when relevant (for example `fix #6`).

PRs should include:
- Clear summary of user-visible and internal changes.
- Linked issue(s) when applicable.
- Screenshots/GIFs for UI changes (`web/`).
- Brief manual verification notes (what you tested with `pnpm dev`/`pnpm build`).
